# Evidence and Attribution Policy

## Evidence levels

| Level | Meaning | Examples |
|---|---|---|
| A | Organizer / conference primary source | UPSide official page, Dunamu release, .HACK session page |
| B | Participant-owned primary artifact | GitHub repository, personal technical blog, portfolio |
| C | Reputable secondary source | News article quoting Dunamu / organizer materials |
| D | Inference | Topic relationship or identity mapping not explicitly documented |

## Attribution rules

1. Do not merge aliases and real names without direct public evidence.
2. Do not treat an educational assignment as a final cohort project unless an official source says so.
3. A project appearing again at a conference may be marked as a **follow-up/continuation** when the project/team identity is explicit; otherwise mark the relation as `probable_follow_up`.
4. `not_found_publicly` means only that the current search failed to locate a public artifact.
5. Publication date alone is insufficient to assign a technical article to a cohort.
6. Record contradictory sources rather than silently choosing one.

## Source priority for technical verification

1. Official project description / presentation
2. Project repository
3. Protocol specification / official documentation
4. Audit / incident report
5. Paper
6. Participant technical article
7. Secondary media

## Revision discipline

Every meaningful reclassification should be recorded in `corrections/revision-log.md` with:

- initial interpretation
- why it seemed plausible
- evidence found
- revised interpretation
- what changed in the taxonomy
